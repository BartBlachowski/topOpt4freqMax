# Implementation plan: three-table performance methodology

Status: **revised plan only — no implementation code is authorized by this document.**

Primary runner to be restructured:
`examples/Performance/performance_comparison.m`

This revision supersedes the earlier two-table plan. In particular, **grayness is never a
stationarity threshold**. It is an algorithm-dependent output-quality metric and is
reported, not used to decide convergence. It may still enter acceptance *indirectly* where
a method's own continuation schedule is grayness-triggered; §4.2.3 records that path per
method rather than denying it.

## 1. Scientific design and claim boundaries

The present single comparison table mixes implementation fidelity, local runtime,
paper-reported quantities, and a nominally common tolerance. Those quantities do not
answer one coherent scientific question. Replace it with three explicitly separated
tables:

| Table | Scientific question | Configuration | Permitted claim |
|---|---|---|---|
| **A — Paper-faithful reproduction** | Can each published method be reproduced from its source? | Each method's complete native, source-paper protocol | Implementation fidelity only |
| **B — Controlled benchmark** | Under identical external engineering requirements, how much computation does each implementation require? | Common external protocol; native internal algorithm retained | Controlled runtime and speedup claims |
| **C — Benchmark sensitivity analysis** | How much does replacing the native protocol with the controlled protocol change each method? | Paired native and controlled runs on the same local platform and mesh | Within-method protocol sensitivity |

The tables must be generated by separate campaign modes, stored in separate result files,
printed separately, and discussed in separate manuscript paragraphs. No row may combine
a paper-native runtime with a controlled-benchmark runtime.

Table A is evidence that an implementation is credible enough to benchmark. A mismatch
does not get tuned away or omitted: it is reported, investigated, and carried as a
limitation into the interpretation of Table B.

That limitation is enforced, not merely narrated. §3.5 assigns a preregistered fidelity
verdict to every Table A row, and §4.5 binds the wording of every Table B speedup to the
verdict of the comparator it is computed against. A method whose reproduction fails may
still be benchmarked — excluding it would be worse — but no speedup measured against it
may be stated as a speedup over the published method.

## 2. Protocol ledger and provenance

Before running any campaign, create a machine-readable protocol ledger with one record
per method and source-paper case. Each record must cite the paper version and the exact
page, equation, table, figure, or code release supporting every setting:

- geometry, boundary conditions, loads, and mesh;
- material, stiffness, mass, and interpolation models;
- objective and constraints;
- optimizer and optimizer-specific parameters;
- stopping test, tolerance, and iteration limit;
- filter/projection type and radius convention;
- move limit and density lower bounds;
- penalization and continuation schedules;
- any iteration-indexed continuation schedule, together with the minimum iteration count
  it imposes before acceptance is possible at all (§4.2.3);
- volume-constraint enforcement mechanism — exact projection, bisection, or soft
  constraint — and the method's own volume tolerance (§4.2.1);
- initialization and random seed, if applicable;
- eigensolver, mode count, shift or target, tolerance, and start-vector policy (§6.1);
- mode handling, multiplicity treatment, and tracked mode count;
- post-processing and the design on which the published frequency is evaluated.

Every reference value and setting receives one of exactly these provenance labels:

- `reported`: explicitly stated in the source;
- `inferred`: derived from source material, with the inference formula and uncertainty
  recorded;
- `unavailable`: neither reported nor defensibly inferable.

Do not silently fill an unavailable source setting from the controlled benchmark. An
inferred setting must be visibly marked in Table A or its notes. For example, Yuksel
published iteration counts inferred from total time divided by rounded time per iteration
must be marked `inferred` and shown with the resulting interval, not as exact integers.

For the Proposed method, “paper-faithful” means the manuscript-native configuration. It
must be written into and versioned with the ledger before Table A results are inspected;
otherwise its native settings could be selected retrospectively.

### 2.1 Freeze record

This document uses “frozen”, “preregistered”, and “before results are inspected” in many
places. None of those are verifiable by assertion. Every such commitment is written into a
single **freeze record** — one committed file — and the ordering is made checkable by
version control rather than by narrative.

The freeze record contains:

- the Proposed method's native configuration (§2);
- the Table A fidelity verdict rule and its thresholds (§3.5);
- the Table A topology metric, binarization threshold, and agreement categories (§3.3);
- `τ`, `εV`, `W`, the calibration data that produced them, and the written justification
  (§4.2.1);
- the common outer budget `Nmax` and its calibration basis (§4.3);
- the terminal-validation procedure and common eigensolver configuration (§4.4.1);
- the timing boundary, warm-up policy, repetition count, run-order policy, and the
  machine-failure rule permitting an outlier to be discarded (§4.4);
- the mesh list and the threshold-sensitivity grid (§7);
- the numerical bounds used by the invariance and determinism tests (§6).

Rules:

- The freeze record is committed before the campaign it governs runs. Its commit hash is
  recorded in the campaign artifacts and cited in the manuscript.
- A frozen value is changed only by a new commit that states what changed, why, and what
  had already been observed at the time. §4.2.1 and §4.3 each permit exactly one such
  revision; both must be visible in history.
- Any quantity discovered to be missing from the freeze record after results are inspected
  is reported as an unpreregistered choice, not retrofitted.

## 3. Table A — paper-faithful reproduction

### 3.1 Execution

Run one row per `(method, published case)`, using the mesh and complete protocol of that
method's source. Table A intentionally does not force a common mesh or common stopping
rule.

The source-paper implementation includes native continuation, optimizer, termination,
post-processing, and initialization. A safety cap may protect the campaign, but it is not
a substitute stopping rule: if hit, the row is reported as `CAP HIT` and cannot be called
a successful reproduction.

The Proposed method uses its frozen manuscript-native protocol. Its published reference
column is “manuscript reference” until the manuscript is published.

### 3.2 Required columns

At minimum:

| Method | Case / mesh | ω₁ ours | ω₁ paper | Signed relative error | Topology agreement | Native iterations ours | Published iterations | `ρ_iter` | Stage 1 | Stage 2 | Total | Native runtime ours | Provenance | Verdict |
|---|---|---:|---:|---:|---|---:|---:|---:|---:|---:|---:|---:|---|---|

Use

`relative error [%] = 100 (ω₁,ours - ω₁,paper) / ω₁,paper`.

Show the sign; do not report only an absolute error. State frequency units and whether
the source reports angular frequency or cyclic frequency.

For Yuksel, always show `Stage 1 + Stage 2 = Total`. Use an em dash, not zero, for methods
without stages. The same stage decomposition is required in Tables B and C.

“Native runtime ours” is measured locally and is descriptive. A source-paper runtime may
be retained in the provenance ledger, with its source hardware, but it must not be used
for a speedup or placed in a column that invites direct comparison with local controlled
runtime.

`Verdict` and `ρ_iter` are defined in §3.5. Both are consumed by Table B: the verdict fixes
the permitted speedup wording and `ρ_iter` is quoted alongside any speedup measured against
a comparator that is not `reproduced`.

### 3.3 Topology agreement

Topology agreement must be reproducible rather than an unqualified visual judgment:

1. If the source provides a density field, evaluate a preregistered field metric and a
   solid-region intersection-over-union (IoU).
2. If only a published image is available, record the digitization, crop, scale, mirror
   convention, and threshold; permit no case-specific free-form warping.
3. If neither supports a defensible numerical comparison, report `unavailable` and show
   the two images side by side for qualitative inspection.

The metric, binarization threshold, and any agreement categories must be frozen before
the reproduction results are evaluated.

### 3.4 Method-specific requirements and known gaps

**Yuksel–Yilmaz**

- Restore all source-paper settings, including the native `0.01` stopping tolerance for
  both stages, source filter radius, lower bounds, move limit, continuation, OC update,
  and uniform initialization.
- Remove the artificial Stage-1 200-iteration cap. It belongs to a different algorithm
  and is not part of this method.
- Give Stage 1 a generous safety budget and let its native convergence test determine
  the handoff to Stage 2.
- Resolve the paper's solid-void post-processing step from the cited procedure. If it
  cannot be reproduced unambiguously, mark it `unavailable`, report the omission, and
  evaluate both the raw and any explicitly documented post-processed design separately.
- Mark paper iteration counts derived from rounded runtime data as `inferred`, including
  their uncertainty interval.

Existing exploratory results indicate that restored paper settings may still leave a
mesh-dependent iteration-count discrepancy, especially in the Stage-2 max-change tail.
That discrepancy belongs in Table A's discussion and must not be removed by retuning.

**Olhoff–Du**

- Reuse the source extraction and reproducibility evidence already under
  `analysis/OlhoffApproachExact/` and `docs/olhoff_audit.md`.
- Resolve known differences such as the extra grayness penalty, the MMA subproblem
  treatment, continuation behavior, and stopping logic before declaring the row
  paper-faithful.
- If the published baseline frequency or topology remains unreproducible, show the
  discrepancy and candidate explanations with provenance rather than substituting a
  convenient local baseline.

**Proposed**

- Freeze its native manuscript settings in the protocol ledger: objective, initialization,
  convergence rule, tolerances, filter, move limit, interpolation, mode handling,
  continuation, and post-processing.
- Do not borrow Table B settings when populating Table A.

### 3.5 Fidelity verdict rule

Table A currently reports quantities but reaches no conclusion, which leaves the judgment
in §1 — “credible enough to benchmark” — to be made after the numbers are seen. Every row
therefore receives one verdict, assigned **mechanically** by the rule below from the frozen
thresholds in the freeze record (§2.1). The rule is frozen before the reproduction campaign
runs; no row is re-categorized by judgment afterwards.

Provisional thresholds, to be confirmed or revised once in the freeze record:

| Verdict | Condition |
|---|---|
| `reproduced` | `\|signed relative ω₁ error\| <= 2%`, topology agreement at or above the frozen threshold (or `unavailable` with a documented qualitative match), no `CAP HIT`, and no required setting marked `unavailable` |
| `partially reproduced` | `\|signed relative ω₁ error\| <= 10%` but topology agreement or iteration count disagrees materially, or a required setting is `unavailable` |
| `not reproduced` | anything else, including `CAP HIT`, or a result lying outside the interval of an `inferred` reference |

Each row also reports the iteration-count fidelity ratio

`ρ_iter = iterations_ours / iterations_paper`,

with its interval whenever the reference is `inferred`. `ρ_iter` is the quantity §4.5
requires to be quoted alongside any speedup computed against a comparator that is not
`reproduced`.

Two known cases fix the intent. The Yuksel–Yilmaz reference iteration counts are not
printed in the source; they are inferred as total time divided by rounded time per
iteration, and the reconstruction under fully paper-faithful settings gives 249 vs 261 at
160×20, 342 vs 208 at 240×30, and 740 vs 180 at 320×40 — our count rising under refinement
where the source's falls. Under the rule above those rows are not `reproduced`, the
reference is `inferred`, and both facts travel with every Table B number computed against
that method. If the Olhoff–Du baseline frequency or topology likewise remains
unreproducible, its verdict follows the same rule rather than a narrative exception.

A verdict of `not reproduced` does not remove a method from Table B. It constrains what
Table B is allowed to say (§4.5).

## 4. Table B — controlled benchmark

### 4.1 What is controlled

Use the same:

- compatible geometry, boundary conditions, physical model, material data, volume
  target, and mesh;
- hardware, operating system, MATLAB release, BLAS/thread settings, compiler/MEX build,
  and numerical precision;
- diagnostics, plotting, image output, and unrelated file I/O disabled;
- outer iteration budget;
- timing boundaries, warm-up policy, repetition count, and run-order policy;
- acceptance test defined below.

If the physical model cannot be made identical without changing a method's scientific
identity, exclude that case from the primary controlled table and explain why. Do not
label an approximate substitution “controlled.”

Do **not** force identical internal algorithms. Each method retains its own objective,
optimizer, update equation, continuation strategy, projection/filter machinery, mode
handling, and stage structure.

### 4.2 Common mathematical convergence criterion

Apply the criterion to the common element-wise **physical density field**, not to each
solver's internal design or optimizer variables. Let

`d∞(k) = max_e |xPhys_e(k) - xPhys_e(k-1)|`

and

`rV(k) = |V(xPhys(k)) - Vtarget| / Vtarget`,

with passive/solid/void regions treated identically in the declared volume functional.
The RMS physical-density change is recorded but is not a stopping test.

A run is accepted at the first confirmed iteration `k*` for which the last `W`
iterations all satisfy

- `d∞ <= τ`;
- `rV <= εV`;
- all required linear, eigenvalue, and optimizer solves returned valid finite results;
- the method has entered its final native stage and completed every mandatory,
  preregistered continuation transition;
- the common iteration cap was not hit.

`W = 10` is preregistered. `τ` and `εV` are calibrated once, before the campaign, by the
procedure in §4.2.1; provisional working values are `τ = 0.003` and `εV = 1e-3`. No
threshold may be selected separately by method or tuned after seeing the final ranking. The
manuscript will state the exact inequality convention and window rule.

`k*` is the end of the confirmation window, making the offline result equivalent to an
implementable online `W`-consecutive-iterations rule. If no `k*` exists within the common
budget, report the observation as right-censored (`> Nmax`, `CAP HIT`) and do not compute
a speedup for that row.

#### 4.2.1 Threshold calibration

`εV` is a hard gate, and the three methods do not enforce volume by comparable means. OC
drives the volume to target by bisection at every iteration, so its residual sits at
bisection precision. The Proposed MMA loop projects back onto the volume whenever the
constraint is violated. The Olhoff–Du MMA formulation carries volume as two soft one-sided
constraints, and its own internal acceptance tolerance is `2e-3` absolute at
`volfrac = 0.5` — `4e-3` relative, four times the provisional `εV`. A blind `εV` therefore
risks right-censoring one method for a constraint-handling convention rather than for
computational cost, which would invalidate the controlled comparison rather than inform it.

`εV` is set from measured data, not asserted. Before thresholds are frozen:

1. log `rV` per iteration (§5) on a pilot sweep covering every method at the smallest mesh
   and one representative production mesh — `rV` has never been recorded, so no existing
   artifact supports any value;
2. record, per method, the smallest `rV` sustained over `W` consecutive iterations in the
   converged tail;
3. set `εV` from the **worst** method's sustained feasibility floor plus a documented
   margin.

Apply the same procedure to `τ`, using the sustained `d∞` floor. Record the calibration
data, the chosen values, and the justification in the freeze record (§2.1).

If no single `εV` admits every method, that is a finding to report — the methods do not
share a common feasibility standard — not a licence to relax the gate per method.

#### 4.2.2 What acceptance does and does not certify

Acceptance certifies stationarity of the physical density field and volume feasibility. It
does not certify that the accepted designs are of comparable quality, and it is not a KKT
or optimality test. Three consequences are binding:

- every efficiency statement is phrased as “time-to-common-acceptance under this protocol”,
  never as “time to converge” or “time to solve”;
- ω₁ is reported for every row on a common footing (§4.4.1), because terminal discreteness
  differs by a factor of several between methods and ω₁ evaluated on a gray SIMP design is
  not comparable to ω₁ on a near-discrete one — without the common evaluation the ω₁ column
  cannot perform the outcome-quality role assigned to it here;
- the fraction of design variables sitting at their move limit is recorded at `k*`. A run
  accepted while a large fraction is still step-limited is stationary only because its
  steps are bounded, and is flagged in the Table B notes. This matters because move limits
  are deliberately left uncontrolled (§4.1) and at least one method reduces its own move
  limit adaptively.

#### 4.2.3 Grayness and continuation floors

**Grayness is never a stationarity threshold in this acceptance rule.** It is not compared
against any tolerance in the list above. Final grayness is reported so that runtime is
interpreted alongside output discreteness.

Grayness can nevertheless enter acceptance *indirectly*, and the earlier claim that it is
“never part of this acceptance criterion” was too strong to be defensible. Acceptance
requires every mandatory continuation transition to be complete, and a method's continuation
may be triggered by its own grayness measure: the Olhoff–Du implementation advances `β`
early when its grayness falls below `gray_tol`. That path is legitimate — it is native
algorithm behavior, not a benchmark tolerance — but it is declared in the ledger (§2) and
reported, not denied.

The same clause has a second consequence. A continuation schedule indexed by iteration
imposes a **floor** on `k*` that is independent of convergence.

The Olhoff–Du implementation has *two* `β` continuation paths and the configuration selects
between them, so the floor must be read from the live one:

- **discrete** (`beta_continuous = false`): a seven-entry schedule advanced every 40
  iterations with a 40-iteration minimum polish at maximum `β`, giving a floor of 280;
- **continuous** (`beta_continuous = true`, which the benchmark configuration selects
  because it sets `filter.heaviside`): `β = βmax^(it/T)` with
  `T = min(300, 0.7·maxiter)`, so `β` saturates at iteration `T` — 300 under any campaign
  budget above 429.

Under the continuous path the discrete schedule's constants are dead code, and `maxiter`
stops being a pure safety budget: it parameterizes `T`. Two runs of this method that differ
only in their iteration budget are therefore *not* comparable if either budget falls below
429, which is a trap for the paired extension test of §6.3 as well as for the campaign.

Either way the floor is real and mesh-independent: the observed Olhoff iteration counts are
flat at 343–374 across a 25× range of element counts, while the other two methods vary by an
order of magnitude. Left unreported, that row measures a hard-coded constant rather than a
convergence rate. Therefore:

- every iteration-indexed schedule floor is declared in the ledger before the campaign;
- the iteration `k_cont` at which the last mandatory continuation transition and any
  minimum-polish requirement were cleared is recorded and reported per row (§4.5);
- the Table B discussion states, per method, how much of `k*` is schedule floor (`k_cont`)
  and how much is convergence (`k* - k_cont`), and no speedup is interpreted as an
  algorithmic result without that decomposition in view.

### 4.3 Offline convergence evaluation

Use a two-pass design:

1. **Discovery pass.** Disable only the method's final native termination, run every
   solver with the same generous outer budget, and record the lightweight history in §5.
   Preserve native stage handoffs and continuation transitions; for example, Yuksel's
   Stage-1 convergence test still controls its handoff to Stage 2. Evaluate `k*`
   retrospectively with a pure common evaluator.
2. **Timed replay.** Replay deterministically to the discovered `k*` with history and
   diagnostics disabled. Use the same accepted design and perform one common terminal
   evaluation. Repeat according to the timing policy below.

The discovery pass establishes convergence without rewriting each solver around a foreign
stopping rule. The clean replay prevents logging overhead from contaminating runtime
claims. Discovery and replay terminal density checksums must agree within the validation
tolerance.

The common outer budget counts all optimization updates, including both Yuksel stages. It
must be fixed before the full campaign and identical across methods. Select it from a
documented calibration run with margin above the slowest observed convergence; do not
silently extend only a favored method. If the budget proves insufficient, mark all
affected campaign results provisional, increase the common budget for every method, and
rerun the affected mesh block.

### 4.4 Timing protocol

The primary Table B runtime is wall time from entry into method-specific initialization
through the accepted update and one common terminal validation, excluding configuration
file parsing, plotting, table generation, and result-file I/O. Also retain optimization
loop time as a secondary diagnostic.

- Record CPU, RAM, OS, MATLAB release, BLAS, thread count, compiler/MEX flags, and commit.
- Use an otherwise idle machine and a fixed power/performance policy.
- Perform one untimed warm-up for each method/mesh execution path.
- Use at least three timed repetitions, interleave or randomize method order within each
  mesh block, and report median plus dispersion (IQR or full range).
- Store every repetition; do not discard outliers without a preregistered machine-failure
  rule.
- Randomizing method order must not change any trajectory. A solver that draws from a
  shared global random stream — including an eigensolver with an unpinned start vector —
  makes run order an input to its own result, so §6.1 must be closed before this policy is
  applied. Otherwise the measure taken to remove thermal and ordering bias silently
  introduces trajectory bias.
- Compute speedup only from runs in the same controlled campaign and state the baseline.
  Report uncertainty and avoid false precision.

#### 4.4.1 Common terminal validation

The terminal validation is one fixed procedure, applied identically to every accepted
design and inside the timing boundary:

1. take `xPhys` at `k*`;
2. binarize it at a volume-preserving threshold — the threshold is resolved per design by
   bisection so that the binarized field has volume `Vtarget`, which removes the choice of
   a fixed cutoff as a free parameter;
3. evaluate ω₁ on both the raw `xPhys` and the binarized field, using one common
   eigensolver configuration: same solver, mode count, shift or target, tolerance, and
   start-vector policy for every method, declared in the ledger (§2).

Both frequencies are reported (§4.5). This exists because the methods currently terminate
at terminal grayness spanning roughly 0.013 to 0.257 — a factor of about twenty — and a
frequency read off designs of such different discreteness cannot serve as the outcome-quality
guard §4.2.2 relies on. Fixing the eigensolver configuration additionally prevents ω₁
differences that originate in solver settings rather than in the design, which matters
because Table A quotes signed relative errors at a precision those settings can reach.

### 4.5 Required Table B outputs

At minimum:

| Method | Mesh | ω₁ raw | ω₁ binarized | Stage 1 | Stage 2 | `k_cont` | Total `k*` | Runtime | Speedup | `d∞` | `rV` | Grayness | Acceptance |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|

Also archive RMS change, native objective, mode information, memory, loop time, the
move-limit-active fraction at `k*`, and all repetition-level timing. A computational-efficiency
claim must be phrased as “time-to-common-acceptance under this protocol,” with both ω₁
columns and grayness visible beside it; it is not a claim that the methods solve identical
internal optimization problems.

Speedup wording is bound to the comparator's Table A verdict (§3.5):

| Comparator verdict | Permitted wording |
|---|---|
| `reproduced` | “X is N× faster than the Y method under this protocol” |
| `partially reproduced` | as above, with the residual discrepancy and its direction stated in the same sentence |
| `not reproduced` | “X is N× faster than **this implementation of** Y under this protocol”, with `ρ_iter` and its interval quoted in the same sentence |

Reported speedup uncertainty combines timing dispersion (§4.4) with acceptance-index
dispersion (§6.5). A speedup quoted without both is not reportable, because `k*` and the
runtime are not independent: the runtime is measured on a replay to `k*`.

## 5. Required iteration history

Add opt-in, preallocated logging without extra eigensolves or other expensive diagnostics.
For every iteration record:

- global iteration and method-native stage/local iteration;
- `max(|ΔxPhys|)` and `RMS(|ΔxPhys|)`;
- native objective value, with sign and definition stored in metadata;
- cumulative elapsed wall time;
- volume residual `rV`, which is required by the §4.2.1 calibration and is not recorded by
  any existing artifact;
- fraction of design variables at the move limit (§4.2.2);
- grayness, using one documented reporting definition;
- tracked mode index, if naturally available;
- MAC, only if already computed by the native method;
- `ω₁`, only when naturally available in that iteration.

Record explicit stage-transition and continuation-transition markers. Missing
method-inapplicable quantities remain `NaN`/`unavailable`; they must not trigger additional
modal analyses merely to fill a column.

Full density fields need not be stored each iteration. Retain deterministic checksums and
the density at validation checkpoints; recover the accepted design with the deterministic
timed replay.

## 6. Required trajectory-invariance proof

Offline evaluation is valid only if three things hold: the solvers are deterministic,
extending a run past its native stopping point leaves the entire prefix unchanged, and the
accepted iteration `k*` is itself stable. Establish all three before trusting any Table B
campaign. The first and third were previously assumed; they are now tested.

### 6.1 Determinism precondition

Determinism is a precondition to be proven, not an assumption. Nothing else in §6 is
meaningful until it holds, because both the paired extension test and the timed replay
compare two separate executions.

- Audit every source of randomness reachable from a solver call. MATLAB's `eigs` generates
  a random start vector unless one is supplied; the Olhoff–Du loop calls
  `eigs(Kf,Mf,J,'SM',optsSM)` at every iteration with only `tol`, `maxit`, and `disp` set,
  and its retry path conditionally seeds `v0` from the previous iterate, which makes the
  trajectory history-dependent as well. The Proposed solver's cached baseline eigenpair is
  computed the same way.
- Pin the start vector and every other stochastic input for every solver, or demonstrate
  empirically that it does not affect the result.
- Demonstrate, per method and per mesh, that repeated runs from identical inputs produce
  bit-identical density fields, iteration counts, and scalar histories — including runs
  executed in a different order within a session, since a shared global random stream makes
  run order an input (§4.4).

The existing instrumentation check covers one method at one mesh
(`instrumentation_validation.json`: Proposed, 160×20, bit-identical, and the easiest case
in the campaign since its eigensolve is on a fixed baseline matrix). That is a starting
point, not the required evidence.

If bit-identical repetition cannot be achieved, the offline design in §4.3 is not usable as
specified, and the common criterion must be evaluated online inside each solver instead.
That is a smaller change than it appears — the criterion is a predicate on `xPhys` — and it
would remove the replay and prefix-invariance burden entirely.

### 6.2 Static audit

For each solver, document every use of its tolerance, maximum-iteration value, and stop
flag. Verify that bypassing termination changes only whether another iteration is entered,
not an update, continuation decision, stage handoff, random stream, or solver state before
the native stopping point.

### 6.3 Paired extension test

For each method on at least a small and a representative production mesh:

1. run with the native stopping rule;
2. rerun from the identical initialization with only final native termination disabled,
   leaving all internal stage handoffs and continuation decisions active;
3. compare every recorded scalar through the native stopping iteration;
4. compare the physical density and relevant solver state at that iteration;
5. continue for a preregistered validation horizon beyond that point.

Require bitwise equality where the execution is deterministic. Otherwise preregister a
tight numerical bound (proposed `max|ΔxPhys| <= 1e-12`) and justify it. Any earlier
divergence blocks offline gating until explained.

This test establishes prefix reproducibility only. It does not establish that the accepted
index is reproducible, which is a separate and stronger requirement; see §6.5.

### 6.4 Instrumentation and replay tests

- logging off versus logging on: identical trajectory and accepted design;
- extended discovery prefix versus clean replay to `k*`: identical accepted design and
  terminal metrics;
- history evaluator tested on synthetic pass, transient-pass, volume-fail, invalid-solve,
  and cap-hit histories;
- quantify logging overhead even though discovery timing is not used for speed claims.

Publish the invariance report and checksums as campaign artifacts. A source-code argument
alone is not sufficient.

### 6.5 Acceptance-index stability

Prefix agreement is necessary but not sufficient. The quantity Table B reports is `k*`, and
`k*` is an extreme order statistic read through a persistence window. Near termination the
stopping test is controlled by a handful of elements: the audit measures a final max/P95
step ratio of 374 at 320×40, with fewer than 5% of elements controlling the result after
iteration 542, while the mean step is `1.16e-5` against a `3e-3` threshold. In that regime a
perturbation far below the §6.3 bound can flip `d∞ <= τ` at a boundary iteration and move
`k*` by hundreds of iterations. Agreement to `1e-12` on the trajectory therefore does not
imply agreement on `k*` at all, and `k*` is what the campaign publishes.

The timing design in §4.3 cannot detect this on its own, because every timed replay runs to
one pre-discovered `k*`; the repetitions measure machine noise and nothing else. So:

- repeat the **discovery** pass at least three times per method on the smallest mesh and one
  representative production mesh;
- report the dispersion of `k*` and of `k_cont` across those repetitions;
- propagate `k*` dispersion into the reported Table B uncertainty and into every speedup
  interval (§4.5);
- if `k*` dispersion is large relative to the between-method differences it is being used to
  establish, the ranking is not reportable and the finding is published as such.

This test is also the natural place to detect a determinism failure that §6.1 missed: a
non-zero `k*` dispersion with pinned inputs means the trajectory is not reproducible.

## 7. Table C — benchmark sensitivity analysis

Table C is recommended as a main or supplementary manuscript table, not an informal
diagnostic. It explains why Tables A and B differ without mixing their claims.

Use paired runs of the same method, mesh, hardware, software, timing boundary, and
terminal evaluator:

- **native arm:** the frozen source/manuscript-native protocol;
- **controlled arm:** the Table B external protocol and common acceptance rule.

Only meshes available to both arms are paired. A paper runtime measured on other hardware
is never an input to Table C.

Required columns:

| Method | Mesh | Native Stage 1/2/Total | Benchmark Stage 1/2/Total | Native runtime | Benchmark runtime | Native ω₁ | Benchmark ω₁ | Δiterations | Δruntime | Δω₁ |
|---|---|---|---|---:|---:|---:|---:|---:|---:|---:|

Define every delta as `controlled - native`, and include relative deltas in the archived
data. Also retain native and controlled grayness and volume residual. Table C supports
within-method statements about protocol sensitivity, especially the change in Yuksel
Stage 2 under the stricter common stationarity criterion. It does not support a
cross-method speed ranking.

Because the criterion is evaluated offline, add a supplementary threshold-sensitivity
panel without rerunning the solvers. Evaluate a small preregistered grid around `τ` and
`εV` and report whether the runtime/iteration ranking changes. Grayness remains an output
for every grid point, never a gate.

### Cost expectation

The earlier 3–5 hour estimate is no longer credible because a scientifically defensible

after it — a censored comparator, or a `k*` that does not reproduce.

## 10. Risks and mitigations

| Risk | Consequence | Mitigation |
|---|---|---|
| Source setting is absent or ambiguous | “Paper-faithful” cannot be established | Mark `unavailable` or documented `inferred`; never replace silently |
| A faithful implementation still disagrees with the paper | Fidelity remains uncertain | Publish the discrepancy, uncertainty, topology evidence, and plausible explanations |
| Source methods use incompatible physics/objectives | Misleading controlled claim | Restrict primary Table B to compatible cases and state exclusions |
| Grayness differs substantially | Runtime ranking may hide output-quality differences | Report grayness beside ω₁; never use it as a stationarity threshold |
| Accepted designs differ in discreteness | ω₁ is not comparable across rows, so the outcome-quality guard fails | Common volume-preserving binarized terminal evaluation with one eigensolver configuration (§4.4.1) |
| Continuation schedule sets a floor on `k*` | Runtime measures a hard-coded schedule, not a convergence rate | Declare floors in the ledger; report `k_cont` and `k* - k_cont` separately (§4.2.3) |
| `εV` incompatible with a method's constraint handling | A comparator is right-censored for a convention rather than for cost | Calibrate `εV` from measured `rV` floors before freezing (§4.2.1) |
| Solver is not bit-reproducible | Replay, prefix invariance, and `k*` are all invalid at once | Prove determinism first and pin eigensolver start vectors (§6.1); otherwise evaluate the criterion online |
| `k*` flips at a boundary iteration | Speedup uncertainty is understated and may be qualitatively wrong | Repeat the discovery pass and propagate `k*` dispersion (§6.5) |
| Comparator fails reproduction | Speedup reads as a method-level claim it cannot support | Bind speedup wording to the frozen fidelity verdict and quote `ρ_iter` (§3.5, §4.5) |
| Preregistration cannot be verified | “Frozen before” is unfalsifiable | Commit the freeze record and cite its hash (§2.1) |
| A transient crosses the common thresholds | Premature convergence | Use the preregistered consecutive-iteration window |
| A method misses the common gate | Undefined time-to-convergence | Report right-censored cap hit; no extrapolated runtime or speedup |
| Extended mode or logging changes a trajectory | Offline iteration count is invalid | Block the campaign on the paired invariance tests |
| Replay differs from discovery | Timed runtime is not tied to accepted design | Check terminal density and metric checksums for every replay |
| Mode switching makes ω₁ histories incomparable | Misinterpreted objective behavior | Log native mode/MAC only when available; use a common terminal eigensolve |
| Timing noise or thermal/order bias | Unstable speedup | Warm up, interleave order, repeat, and report dispersion |
| Figure-derived topology metric is subjective | Overstated topology agreement | Freeze deterministic digitization/registration or report unavailable |
| Yuksel Stage 1 is truncated | Inflated Stage 2 and invalid total count | Remove the artificial cap and show all three stage counts |
| Post-processing changes ω₁ | Wrong reproduction target | Record raw and source-post-processed designs separately |
| Campaign cost grows with common `Nmax` | Incomplete sweep | Calibrate once, checkpoint per run, and forecast before full launch |

## 11. Reviewer-facing justification

Table A asks whether the implementations represent the cited algorithms. It preserves
each paper's native choices and exposes missing information, inferred quantities, and
residual discrepancies. Its runtime is descriptive and supports no speed claim. It now also
reaches a verdict by a rule frozen in advance, so that “credible enough to benchmark” is a
decision the protocol makes rather than a judgment made after the numbers are seen.

Table B asks a different question: how quickly the implementations meet the same external
engineering acceptance test on the same machine and model. It equalizes the physical
density stationarity test, volume feasibility, iteration budget, timing boundary, and
environment while preserving the internal identity of each algorithm. Grayness and ω₁
remain visible outcome metrics, preventing a fast but qualitatively different design from
being presented without context — and because terminal discreteness differs by roughly a
factor of twenty between methods, ω₁ is reported on a common binarized design as well as on
the raw one, so that the outcome-quality guard is itself comparable.

Table B states plainly what its acceptance test does not do. It does not certify optimality,
it does not certify equal design quality, and where a method's continuation schedule imposes
an iteration floor it reports that floor separately from the converged remainder. Its
speedups are worded according to the fidelity verdict of the comparator they are measured
against, so a reader can never mistake a statement about this implementation of a published
method for a statement about the published method itself.

Table C quantifies how much the benchmarking protocol itself changes each method. The
paired stage counts, runtimes, and frequencies explain differences between native
reproduction and controlled execution—particularly Yuksel's Stage-2 sensitivity—without
confusing those differences with implementation errors or cross-hardware speedups.

Together the three tables separate fidelity, controlled computational efficiency, and
protocol sensitivity. That separation is more defensible than a single mixed table
because every number has one configuration, one provenance, one timing basis, and one
scientific claim.
